# Add a unit

1. Create `unifold.yaml` in the folder from [unifold.template.yaml](../assets/unifold.template.yaml). The folder name is the unit's name. Required: `responsibility`, one sentence. Give a `kind` where one fits: `logic`, `stateful` and `adapter` carry rules. Say what it runs as, `runs-as: library`, `process`, `job`, `ui` or `firmware`. Write `not`, what the unit leaves to others, one line each; what it hides is the first sentence of `## Why`. Set `status: planned` if the code does not exist yet.
2. Declare capabilities and needs, each with a `summary` and a `contract`; the one-line form `name: summary` is for a draft or an optional need that nothing connects yet. A need that is only passed up, or a capability that a child implements, may be an empty entry (`clock:`): it takes summary and contract from the one line that wires it. Write a need from the point of view of this unit: what is needed, never who has it. Do not declare the language runtime, registry packages or logging as needs.
3. Add a `wiring` line for every need to the parent's manifest (`new-unit.need: sibling.capability`). Where no sibling meets a need, declare it in the parent too and pass it up: `new-unit.need: need`. Add a line for each sibling need that the new unit meets.
4. Give both sides of every new connection the same `contract`: a document in `docs/references/` of the parent or a unit above it. Write it if it does not exist ([write-a-contract.md](write-a-contract.md)). A side that uses only some parts lists them under `contract: {path, parts}`.
5. Write `README.md` from [README.template.md](../assets/README.template.md). Its `## Why` is the part that matters. Do not list children, capabilities or connections in prose; what the unit does not do is `not` in the manifest. `check --fix` adds the unit to the index in the root `AGENTS.md` when you finish.
6. Add the unit to the scenarios whose story passes through it, or write one ([write-a-scenario.md](write-a-scenario.md)).
7. [Finish](../SKILL.md#4-finish).
